# 전문 생산라인을 추가하는 방법

새 도메인 Factory는 공통 생산 설비를 재사용하고 도메인별 생산 규격을 구현한다. 자동차 공장에서 공통 작업지시·창고·검사 의뢰·출고 통제 위에 차종별 부품과 조립 규칙을 올리는 것과 같다.

현재 프로젝트는 반복되는 공통 기능과 세 개의 명시적 생산라인을 제공한다. 동적 Recipe marketplace나 어떤 요구든 자동으로 소프트웨어를 생성하는 완성된 범용 SDK를 제공하지 않는다.

## 재사용할 부분과 새 라인이 소유할 부분

| 공통 기반에서 재사용 | 새 ProductLine이 정의 |
| --- | --- |
| tenant와 실행 identity, BuildSession 원장·CAS | 제품 요구사항과 허용하는 옵션 |
| 등록 Action·권한·승인·실행 직전 통제 | 제품 Blueprint와 설계 규칙 |
| Worker transport와 작업지시 전달 | 모듈 catalog, 선택 규칙, 생성·수정 지시 |
| immutable artifact와 정확한 hash 참조 | 제품 후보·BOM·bundle 형식 |
| 인증 Component 해석·현재 상태 검사 | 소비 가능한 Component 계약과 호환성 |
| durable dispatch·상태·취소·복구 원칙 | 제품 업무/API 검사와 전체 통합 검사 |
| 검토 요청과 정확한 Decision 결박 | 제품별 approval subject와 출고 계약 |
| provenance·출고 graph 검증의 원칙 | 제품 인계물과 소비자 안내 |

`FactoryProductLine`과 registry는 현재 라인을 명시적으로 선택하고 복구할 수 있는 구성 경계다. 새 라인은 실제 공정과 취소·복구 동작을 연결해야 하며 이름만 추가해서 생산 가능한 상태가 되지 않는다.

## TOS 생산라인의 예

TOS는 확장 방법을 설명하는 예이며 현재 구현된 제품이 아니다. 실제 TOS Factory를 만들려면 먼저 반복 생산할 제품의 범위를 좁혀야 한다. 예를 들어 작업 주문, 선석 계획, 장비 배정 등 어떤 업무와 사용자별 옵션을 지원하는지 정한다.

그다음 검증된 기본 모듈과 선택 모듈 catalog, 요구사항에서 Blueprint로 변환하는 규칙, 조립·빌드 정책과 전체 제품 검사 기준을 구현한다. 기존 모듈로 채울 수 없는 제한된 부분에는 Coding Worker 작업지시와 수정 루프를 사용할 수 있다. 이미 있는 모듈의 조립은 결정적인 도구에 맡길 수 있다.

제품에 Agent Component가 필요하면 정확한 인증 참조를 부품으로 잠근다. TOS의 runtime, connector와 Action 권한에 맞게 연결하고, 전체 제품 검사에서 실제 통합 동작을 검증한다. Factory의 생산 Worker session·workspace·생산 권한을 제품에 그대로 넣지 않는다.

현재 데모는 이미 인증된 부품을 명시적으로 선택해 소비한다. 필요한 부품이 없을 때 자동으로 하위 생산 주문을 만들고, 생산 완료를 기다려 상위 제품에 넣는 범용 기능은 이 데모의 완료 범위가 아니다. 그 기능을 도입하려면 주문 간 소유권·기한·취소·실패·인증 폐기와 예산을 별도로 설계해야 한다.

## 권장 구현 순서

1. 첫 제품의 입력·기능·옵션·출고물을 고정하고 성공·실패 사례를 적는다.
2. Component 소비 계약과 모듈 catalog를 정한다. 재사용 부품과 새로 생성할 부분을 구분한다.
3. 요구사항·Blueprint·WorkOrder·BOM의 정확한 bytes와 provenance 계약을 만든다.
4. 실제 BUILD/VERIFY/REVIEW/RELEASE 경로와 라인 전용 취소·복구를 구현한다.
5. Factory가 소유하는 독립 업무·통합 검사를 만든다. 정상 부품의 잘못된 wiring도 거부한다.
6. 실제 주문을 생산하고 실패·수정·재검사·정확한 사람 승인·출고·읽기 검증을 수행한다.
7. 다른 라인에서 변경 없이 소비할 필요가 있으면 그 소비 계약과 별도의 제품 검사를 검증한다.

새 라인을 추가하면서 기존 인증·출고 기록의 의미를 바꾸거나 오래된 검사 결과를 새 제품의 증거로 승격하지 않는다. 실제로 반복되는 메커니즘이 확인된 부분을 공통 기반으로 추출하고 제품 의미는 라인에 남긴다.

## Digital Organization과 연결하기

Digital Organization은 여러 Factory에 수요를 배정하고 출고 제품을 환경에 배치·운영하는 후속 조직 모델이다. 현재 Factory 내부 scheduler를 조직 전체 운영 제어기로 확장한 구현은 포함하지 않는다.

새 라인의 출고 계약은 Operations Plane이 인계받을 artifact와 provenance를 명시할 수 있다. 환경별 설치와 운영 상태의 정본은 Operations Plane이 소유한다. 자세한 경계는 [생산 공정](production-process.md)을 참조한다.
